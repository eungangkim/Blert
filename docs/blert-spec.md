## 문서 안내

이 문서는 Claude Code가 그대로 읽고 구현할 수 있도록 만든 blert의 기획서와 설계서다. v0.1과 v0.2 구현에 필요한 내용은 모두 채워져 있고, v0.3 이후 항목은 해당 버전 착수 전에 보강한다.

### 기획 범위와 설계 범위

| 구분 | 답하는 질문 | 담는 내용 | 누가 주로 읽나 |
| --- | --- | --- | --- |
| 기획서 (Part A) | 무엇을, 왜 만드는가 | 서비스 정의, 사용자, 결정사항, 기능·비기능 요구사항, 범위 밖, 로드맵, 미결 사항 | 기획자(본인), Claude Code의 작업 판단 기준 |
| 설계서 (Part B) | 어떻게 만드는가 | 구조, 모듈, 명령어 명세, 데이터 모델, 외부 연동, 보안, 실행 모드, 테스트 | Claude Code의 구현 입력 |
| 구현 지침 (Part C) | 어떤 순서와 규칙으로 만드는가 | 단계별 작업 순서, 코딩 규칙, 완료 보고 방식 | Claude Code |

기획서에 없는 기능은 설계서에 들어갈 수 없고, 설계서의 모든 모듈은 기획서의 요구사항 ID 하나 이상에 연결된다. 이 연결은 B12 추적표로 확인한다.

# Part A. 기획서

## A1. 서비스 개요

**한 줄 정의:** 명령어 한 줄로 설치하고, 명령어 몇 개로 바이낸스 현물·선물 알림을 설정해 내 PC에서 데스크톱 알림과 소리로 받는 로컬 CLI 도구.

| 항목 | 내용 |
| --- | --- |
| 서비스 이름 | `blert` (binance + alert). 명령어는 `blert`, npm 패키지명은 `@eungang/blert` (D-76) |
| 모티브 | [sounds.sh](https://www.sounds.sh/) — 한 줄 설치, 큐레이션된 테마 묶음, 터미널을 들여다보지 않아도 되는 알림 |
| 형태 | TypeScript + Node.js CLI, npm 배포 (`npx @eungang/blert ...`, 설치 뒤에는 `blert ...`) |
| 실행 위치 | 사용자 PC (서버 없음) |
| 핵심 가치 1 | 한 줄 설치 + 프리셋 한 줄로 바로 쓸 수 있음 |
| 핵심 가치 2 | 키와 데이터가 사용자 PC 밖으로 나가지 않음 |
| 핵심 가치 3 | 읽기 전용 키만 허용해 최악의 경우에도 자산 이동이 불가능함 |

### sounds.sh 대응표

| sounds.sh | blert |
| --- | --- |
| `npx soundsh find` 한 줄 설치 | `npx @eungang/blert init` |
| 테마 (이벤트 사운드 묶음) | 프리셋 (알림 조건 묶음) |
| 테마 단일 명령 설치 | `blert preset install <이름>` |
| 이벤트별 사운드 | 알림 유형별 사운드 (저작권 없는 음원) |
| 웹 갤러리 | v1.0 프리셋 갤러리 |

## A2. 대상 사용자와 사용 시나리오

주 사용자는 PC 앞에서 작업하면서 바이낸스 시세나 자기 계정 상태를 놓치고 싶지 않은 개발자·트레이더다. 터미널 사용에 익숙하다고 가정한다.

| 사용자 유형 | 특징 | 주로 쓰는 기능 |
| --- | --- | --- |
| 입문 사용자 | 명령어 문법을 모름, 기본값을 그대로 씀 | `init`, 프리셋 |
| 일반 사용자 | 코인별로 원하는 조건이 있음 | 개별 알림 추가·삭제 |
| 고급 사용자 | 반복 정책까지 직접 조정 | `--mode` 등 고급 옵션 |

### 대표 시나리오

| ID | 시나리오 | 목표 버전 |
| --- | --- | --- |
| SC-01 | 처음 설치하고 프리셋 하나로 1분 안에 첫 알림을 받는다 | v0.1 |
| SC-02 | BTC 목표가 알림을 추가하고, 도달하면 소리와 함께 알림을 받는다 | v0.1 |
| SC-03 | 노트북 절전 후 복귀했을 때 감시 중단 구간을 안내받는다 | v0.1 |
| SC-04 | 읽기 전용 키를 등록하고 내 주문 체결 알림을 받는다 | v0.2 |
| SC-05 | 거래 권한이 켜진 키를 등록하려다 거부 안내를 받는다 | v0.2 |
| SC-06 | 선물 포지션 청산가 근접 알림을 받는다 | v0.3 |
| SC-07 | 터미널을 닫아도 백그라운드에서 감시가 계속된다 | v0.4 |

### 시나리오별 단계 흐름

| ID | 사용자 행동 | 시스템 반응 | 성공 기준 |
| --- | --- | --- | --- |
| SC-01 | `npx @eungang/blert init` → 고지 동의 → 사운드 켜기 → 프리셋 `major-swing` 선택 → `blert run` | 설정 폴더 생성, 규칙 3개 등록, 감시 시작 알림 표시 | 설치부터 감시 시작 알림까지 1분 이내 |
| SC-02 | `blert add price BTC above 70000` → `blert run` | 규칙 등록 확인 메시지. 가격 돌파 시 데스크톱 알림 + up 사운드, 규칙은 1회성으로 비활성 | `list --all`에서 비활성 상태로 보임 |
| SC-03 | `run` 중 노트북 덮개를 닫았다가 연다 | 60초 이상 공백 감지 → 재연결 → "감시 중단: 시작\~종료 시각" warn 알림 | 공백 구간이 알림과 로그에 남음 |
| SC-04 | `blert key add` → Ed25519 키 입력 → `blert add fill all` → `blert run` | 키체인 저장, 권한 검사 통과, 체결 시 account 사운드와 알림 | 설정 파일·로그에 키 흔적 0건 |
| SC-05 | 거래 권한이 켜진 키로 `blert key add` | 어떤 권한이 문제인지와 끄는 방법 안내, 저장하지 않음, 종료 코드 2 | 키가 키체인에 남지 않음 |
| SC-06 | `blert add liq f:BTC 5%` → `blert run` | 청산가까지 거리가 5% 이하가 되면 warn 알림, 5분 쿨다운 | Q-01 결과에 따라 흐름 확정 |
| SC-07 | `blert start` → 터미널 종료 → `blert status` | 데몬이 계속 실행되며 status가 실행 중과 규칙 수를 표시 | 터미널을 닫은 뒤에도 알림 수신 |

| D-67 | 서비스 시작 모드 | 서비스가 띄운 데몬(`start --service`, 도움말에 나오지 않는 숨김 옵션)은 시작할 때 필요한 시장에 연결하지 못해도 **종료하지 않고 계속 재시도**하고(D-37 확장) 연결되면 감시 중단 구간으로 알린다. 작업에는 로그인 후 30초 시작 지연을 둔다 | 로그인 직후 네트워크가 아직 없을 때 감시가 조용히 꺼지는 것을 막음 (NFR-REL-02) | 2026-10-06 |
| D-68 | 이미 실행 중일 때 | 서비스 시작은 데몬이나 `run`이 이미 실행 중이면 오류 없이 조용히 끝난다(중복 데몬 없음). `service install`은 실행 중인 데몬을 건드리지 않는다 | 로그인할 때마다 거부 알림이 뜨지 않게 함 | 2026-10-06 |
| D-69 | 외부 채널 정책 | 외부 채널은 **기본 꺼짐**이고 사용자가 직접 켠 선택 기능으로만 쓴다. 등록할 때 "알림 문구가 해당 서비스 서버를 거친다"를 고지하고 y/N 동의를 받는다. 기본 전송 대상은 **공개 시장 알림과 감시 중단 경고**이고, **계정 알림(체결·잔고·청산가, 키 관련 경고)은 별도 스위치를 켠 경우에만** 보낸다. 채널 서비스의 도메인은 채널을 등록했을 때만 허용한다. NFR-SEC-02는 "사용자가 직접 설정·동의한 채널로 알림 문구만 전송"을 예외로 한다. 키·시크릿·계정 식별 정보는 보내지 않는다 | 데이터 통제권을 사용자에게 두면서 폰 알림 목적을 충족 (D-08 대체) | 2026-10-07 |
| D-70 | 연결할 채널 | v1.0은 **텔레그램 봇** 1개를 연결한다. 호출은 `https://api.telegram.org/bot<토큰>/sendMessage`(`chat_id`, `text`). 디스코드·슬랙 웹훅 등 다른 채널은 이후 버전(Q-13) | 설계서 예시이고 폰 푸시로 자리를 비웠을 때도 알림을 받음 | 2026-10-07 |
| D-71 | 채널 설정 방법 | `blert channel add telegram` / `remove` / `test`. 봇 토큰은 명령행 인자가 아니라 **프롬프트로 입력**받고 OS 키체인에 **별도 항목**(`blert-channel-telegram`)으로 저장한다. 대화 ID는 봇에 메시지를 한 번 보내게 한 뒤 `getUpdates`로 자동 탐지하고, 실패하면 직접 입력받는다. 설정 파일(`config.json`)에는 대화 ID와 계정 알림 포함 여부만 남기고 토큰은 남기지 않는다. 키체인이 없는 환경(D-30)에서는 등록을 거부한다. 등록 직후 시험 메시지를 보낸다. 계정 알림 포함 여부는 `channel add`에서 묻고, 등록한 뒤에는 `blert channel account on|off`로 바꾼다(토큰·대화 ID는 그대로 두며, 켤 때는 계정 정보가 외부 서버를 거친다는 고지와 y/N 동의를 다시 받는다) | 키와 같은 원칙(인자·파일·환경변수 금지)으로 비밀을 다룸 | 2026-10-07 |
| D-72 | 채널 전송 범위 | 채널 설정은 두 가지뿐이다: 채널 켜기/끄기(등록=켜짐, `remove`=꺼짐)와 계정 알림 포함 여부. 규칙마다 채널을 고르는 옵션은 두지 않는다. 묶음 요약(D-28)은 데스크톱과 같게 요약 1건으로 보내고, "감시 시작" 알림은 채널로 보내지 않는다 | 명령 문법을 늘리지 않고 단순하게 유지 | 2026-10-07 |
| D-73 | 채널 전송 실패 | 알림당 1회 시도에 짧은 재시도 2회(요청 한도 429는 응답의 대기 시간만큼). 그래도 실패하면 포기하고 데스크톱·소리는 영향받지 않는다. 실패 안내는 한 번만 보이고 로그에 남긴다. 오프라인 동안 밀린 알림은 나중에 다시 보내지 않는다 | 시점이 틀린 알림이 오해를 부름 (NFR-REL-02) | 2026-10-07 |
| D-74 | 배포 버전 | `1.0.0`으로 공개한다. README에 검증된 환경은 Windows이고 macOS·Linux는 자동 테스트(CI)만 통과했으며 데몬·서비스·알림은 미검증임을 명시한다 | 설계서의 v1.0 기준과 일치하고 검증 범위는 사실대로 밝힘 | 2026-10-07 |
| D-75 | 배포 절차 | 구현과 수동 확인이 끝난 뒤 배포한다. ① 사용자가 GitHub 저장소를 `git remote`로 연결해 푸시 ② npm 계정(2단계 인증)에서 토큰을 만들어 저장소 시크릿 `NPM_TOKEN`에 등록 ③ 배포 직전 점검(`npm pack` 내용, 태그와 `package.json` 버전 일치, 의존성 고정, 액션 커밋 SHA 고정) ④ **사용자 승인 뒤** 태그(`v1.0.0`) 푸시로 provenance 배포. 태그 푸시와 `npm publish`는 되돌릴 수 없어 사용자 승인 없이 하지 않는다 | 같은 버전 번호는 다시 쓸 수 없음 (NFR-SEC-04) | 2026-10-07 |
| D-76 | npm 패키지 이름 | 명령어는 `blert` 그대로이고, npm 패키지 이름은 `@eungang/blert`(범위 이름)로 배포한다. `package.json`의 `bin`이 `blert`이므로 `npm install -g @eungang/blert` 뒤에는 `blert ...`를 쓰고, 설치 없이 쓸 때는 `npx @eungang/blert ...`다. 일반 이름 `blert`는 npm이 비슷한 이름(`inert`, `bser`)을 이유로 거부했다(2026-10-07 실제 배포에서 확인, E403). 범위 이름 `@eungang`은 npm이 제안한 것으로 npm 사용자 이름과 같아야 한다 | npm 이름 정책 때문. 범위 이름은 비슷한 이름 검사를 받지 않음 | 2026-10-07 |
| D-77 | 프리셋 공유 방식 (v1.2 예정) | 프리셋은 **파일 방식**(`blert preset install ./파일.json`, 외부 요청 없음)과 **주소 방식**(`blert preset install https://...`)을 모두 지원한다. `https://`로 시작하면 주소, 경로이면 파일, 그 밖에는 내장 슬러그로 구분한다. 자동 갱신은 없고, 새 버전은 다시 설치한다. 설치할 때 출처 주소와 해시를 설정에 기록하고 `preset list`에 보여 준다 | 갤러리 공유를 파일과 주소 모두로 쓸 수 있게 하되, 사용자가 선택하게 함 | 2026-10-07 |
| D-78 | 주소 방식 허용 범위와 안전장치 | 모든 https 주소를 허용하되 **사용자가 명령에 직접 입력했을 때만** 접속한다(자동 요청 없음). 내려받기(GET)만 하고 사용자 정보를 보내지 않으며, 접속한 서버에는 IP가 보인다. https만, 최대 크기 제한(기본 256KB), 10초 제한, 다른 호스트로의 리다이렉트 거부, 쿠키·인증 정보 없음. 설치 전에 출처 주소·규칙 요약·해시를 보여 주고 y/N 동의(기본 No)를 받는다 | 프리셋은 규칙 목록일 뿐 실행 코드가 아니라 위험이 낮지만, 외부 파일이므로 확인 단계를 둠 | 2026-10-07 |
| D-79 | 프리셋 변조 방지 | 설치할 때 해시(SHA-256)를 보여 주고 기록한다. `--sha256 <해시>`를 주면 일치할 때만 설치한다. 형식을 엄격히 검증하고(규칙 개수 상한, 허용된 유형·값만, 소리는 정해진 종류만), 규칙의 출처는 항상 `preset:<슬러그>`로 덮어쓴다 | 서명 없이도 갤러리가 해시를 안내해 검증할 수 있게 함 | 2026-10-07 |
| D-80 | 프리셋 이름 충돌 | 내장 슬러그는 덮어쓰지 못하고, 이미 설치된 슬러그와 겹치면 거절한다(바꾸려면 먼저 `remove`). 슬러그는 영문 소문자·숫자·하이픈만 허용한다 | 내장 프리셋 변조와 경로 문자 삽입을 막음 | 2026-10-07 |
| D-81 | 소리 등록 단위 (v1.1 예정) | 소리는 **종류별 4칸**(`up`, `down`, `account`, `warn`)만 바꿀 수 있다. 규칙마다 다른 소리를 지정하는 기능은 이후 검토한다 | 웹사이트의 "등록할 칸 선택"과 맞고 구현이 단순함 | 2026-10-07 |
| D-82 | 소리 설치 방식 | **파일**(`blert sound set <종류> ./파일.wav`)과 **주소**(`blert sound set <종류> https://... # Part B. 설계서

## B1. 시스템 구조 개요

모든 모듈은 사용자 PC의 한 프로세스 안에서 돌고, 네트워크로 나가는 곳은 바이낸스뿐이다. 판단은 engine 한 곳에서만 한다.

&#91;embedded content: 모듈 구조 · 외부 통신은 바이낸스 한 곳\]

사용자 명령은 cli를 거쳐 store에 규칙으로 저장되고, binance 모듈이 받은 이벤트를 engine이 규칙과 대조해 notify로 내보낸다. runtime은 이 모듈들을 조립하고 실행 모드와 재연결을 맡는다.

## B2. 디렉터리·모듈 구조

모듈은 책임 하나씩만 가진다. 바이낸스 연동, 규칙 판단, 출력은 서로 직접 부르지 않고 이벤트로만 주고받는다. 코드는 TypeScript(strict)로 작성하고 `dist/`로 빌드해 배포한다.

```text
blert/
├─ src/
│  ├─ index.ts      진입점 (bin)
│  ├─ cli/          명령어 파싱, 도움말, 입력 검증, 오타 제안
│  ├─ presets/      프리셋 정의(JSON)와 설치·제거
│  ├─ engine/       알림 규칙 평가, 반복 정책, 폭주 묶음
│  ├─ binance/      공개 스트림, 사용자 데이터 스트림, REST 보충 조회
│  ├─ security/     키체인 저장, 권한 검사
│  ├─ notify/       데스크톱 알림, 사운드, 콘솔, 채널 어댑터
│  ├─ store/        설정·규칙·상태 JSON 저장, 파일 잠금
│  ├─ runtime/      실행 모드, 절전 감지, 생명주기
│  ├─ i18n/         메시지 파일 (ko.json)
│  └─ shared/       로깅, 오류 타입, 공통 유틸, 타입 정의
├─ assets/sounds/   저작권 없는 음원 + LICENSES.md
├─ docs/            이 기획서·설계서
├─ test/
├─ package.json
└─ tsconfig.json
```

| 모듈 | 책임 | 의존 가능 | 첫 버전 |
| --- | --- | --- | --- |
| cli | 사용자 입력을 명령 객체로 변환 | store, presets, security, i18n | v0.1 |
| presets | 프리셋 → 알림 규칙 목록 변환 | store | v0.1 |
| engine | 시장·계정 이벤트를 규칙과 대조, 발동 결정 | store | v0.1 |
| binance | 바이낸스 연결과 이벤트 발행 | security | v0.1 |
| security | 키 보관·권한 검사 | — | v0.2 |
| notify | 발동된 알림을 채널로 출력 | i18n | v0.1 |
| store | 설정 파일과 알림 상태 읽기·쓰기 | — | v0.1 |
| i18n | 메시지 키 → 한국어 문장 변환 | — | v0.1 |
| runtime | 모듈 조립, 실행 모드, 재시작 | 전체 | v0.1 |

`cli`는 `notify`와 `runtime`을 직접 import하지 않는다. `cli`가 정의한 포트 인터페이스(`NotifierPort`, `Runner`)를 진입점(`src/index.ts`)에서 구현체와 연결한다. `presets`가 구현하는 `PresetService`도 같은 방식이다.

### 모듈 간 이벤트

모듈은 runtime이 만든 타입 있는 이벤트 버스 하나로만 통신한다. 모든 이벤트는 `ts`(ISO 8601)를 가진다.

| 이벤트 | 발행 | 구독 | 내용 | 버전 |
| --- | --- | --- | --- | --- |
| `market.ticker` | binance | engine | market, symbol, price, quoteVolume | v0.1 |
| `market.kline` | binance | engine | market, symbol, openTime, close, quoteVolume, closed (1분봉. 백필 데이터도 같은 이벤트로 발행) | v0.1 |

| `account.balance` | binance | engine | asset, free, locked | v0.2 |

  | { type: 'market.ticker'; ts: string; market: Market; symbol: string; price: number; quoteVolume: number }
  | { type: 'market.kline'; ts: string; market: Market; symbol: string; openTime: string; close: number; quoteVolume: number; closed: boolean }

  | { type: 'rule.fired'; ts: string; alert: Alert }

데몬 모드(v0.4)에서는 CLI와 데몬이 다른 프로세스이므로, CLI가 `rules.json`을 쓰면 데몬이 파일 변경을 감지해 `rules.changed`를 발행한다. 감시 방식은 D-56이고 포그라운드 `run`도 같은 코드를 쓴다.

## B4. 알림 모델과 규칙 엔진

모든 알림은 하나의 규칙(Rule) 형식으로 저장된다. 명령어로 만든 알림과 프리셋으로 설치한 알림은 같은 형식이며, 엔진은 출처를 구분하지 않는다.

### 규칙 타입 (초안)

```ts
type Market = 'spot' | 'futures';
type RepeatPolicy =
  | { kind: 'once' }
  | { kind: 'cooldown'; ms: number }          // 1분 ~ 24시간
  | { kind: 'hysteresis'; widthPct: number }  // 기준값 대비 %
  | { kind: 'each' };                         // 이벤트마다 (체결, D-43)

interface Rule {
  id: number;
  type: 'price' | 'change' | 'volume' | 'funding' | 'fill' | 'balance' | 'liq';
  market: Market;
  symbol: string;            // 정규화된 전체 심볼, 예: BTCUSDT. 계정 규칙은 '*'(전체) 가능 (D-43)
  condition: Condition;      // 유형별 조건 (아래 표)
  repeat: RepeatPolicy;
  sound?: 'up' | 'down' | 'account' | 'warn' | 'off';
  name?: string;
  source: 'manual' | `preset:${string}`;
  enabled: boolean;
  createdAt: string;         // ISO 8601
}

interface RuleState {        // 규칙과 분리해 저장 (B8)
  ruleId: number;
  lastFiredAt?: string;
  armed: boolean;            // 히스테리시스 재무장 여부
}
```

### 유형별 조건

| 유형 | 조건 | 판정 방식 | 근거 |
| --- | --- | --- | --- |
| price | 방향(above/below), 가격 | 현재가가 기준을 넘는 순간(미충족 → 충족으로 바뀔 때). 시작할 때 이미 충족 중이면 알리지 않고, 반대편으로 갔다가 다시 넘을 때 알린다. `below`는 아래로 내려가는 순간 | FR-ALERT-01, D-34 |
| change | 퍼센트, 기간, 방향 | 롤링 윈도우: 현재가를 (현재 − 기간) 시점 가격과 비교. 기간만큼의 가격 이력을 메모리에 유지 | D-24 |
| volume | 배수, 짧은 구간, 긴 구간 | 짧은 구간 거래대금 ÷ (긴 구간 거래대금을 짧은 구간 단위로 나눈 평균) ≥ 배수 | D-25 |
| funding | 방향, 퍼센트 | 예상 펀딩비가 기준을 넘는 순간(미충족 → 충족). 시작 시 이미 초과 중이면 알리지 않는다. 기준과 같은 값은 초과가 아니다 | FR-ALERT-04, D-34 |
| fill | 심볼 또는 all (현물), `f:<심볼>` (선물, D-52) | 주문 체결 이벤트 수신 시 | FR-ACC-01, FR-ACC-03 |
| balance | 자산, 퍼센트 | 마지막 알림 시점 대비 잔고가 퍼센트 이상 변동 | D-27 |
| liq | 퍼센트 | 마크 가격과 청산가의 거리가 퍼센트 이하. 시작할 때 이미 이하면 즉시 알림, 쿨다운으로 반복 방지. 포지션이 없으면 알리지 않는다. 롱·숏이 함께 있으면 가까운 쪽 기준 | FR-ALERT-05, D-46, D-47, D-49 |

### 단계별 청산 경고 (v1.3, D-118~D-121)

`liq` 조건에 선택 항목 `stages`(내림차순 퍼센트 배열, 2~4개, 첫 값은 `pct`)를 둘 수 있다. 규칙 상태에는 선택 항목 `liqStage`(지금 들어와 있는 단계, 없으면 밖)를 저장한다.

| 상황 | 동작 |
| --- | --- |
| 거리가 첫 단계 이하로 처음 진입 | 첫 단계 알림 |
| 더 깊은 단계로 진입 | 쿨다운과 무관하게 즉시 알림 |
| 같은 단계에 머무름 | 쿨다운(5분)마다 반복 |
| 얕은 단계로 복귀(여전히 첫 단계 이하) | 알림 없이 단계만 낮춤. 다시 깊어지면 알림 |
| 거리가 첫 임계값의 1.1배를 넘음 | 완전히 재무장. 다시 진입하면 첫 단계 알림 |

알림은 `warn` 소리 하나를 쓰고, 문구에 `n/N단계`를 넣는다(첫 단계 "주의", 마지막 "긴급", 중간 "위험"). `stages`가 없는 규칙은 기존 동작(D-47)과 같다.

### 알림 유형별 기본 반복 정책

| 유형 | 기본 정책 | 버전 |
| --- | --- | --- |
| price | 1회성 | v0.1 |
| change | 쿨다운 30분 | v0.1 |
| volume | 쿨다운 15분 | v0.1 |
| funding | 히스테리시스, 폭 20% | v0.1 |
| fill | 이벤트마다 1회 (반복 정책 없음) | v0.2 |
| balance | 쿨다운 10분 | v0.2 |
| liq | 쿨다운 5분 | v0.3 |

### 반복 정책 동작

| 정책 | 동작 | 기본값·범위 |
| --- | --- | --- |
| 1회성 | 발동 후 `enabled=false`. 삭제하지 않고 보관, `list --all`로 확인 | — |
| 쿨다운 | 발동 후 지정 시간 동안 재발동 금지 | 1분 \~ 24시간 |
| 히스테리시스 | 발동 후 `armed=false`. 값이 기준에서 폭(기준값 대비 %)만큼 반대로 벗어나면 `armed=true`로 재무장 | 가격류 0.5%, 펀딩비 20% |

### 기본 프리셋 (D-23)

| 슬러그 | 표시 이름 | 포함 규칙 |
| --- | --- | --- |
| `major-swing` | 메이저 급등락 | BTC·ETH·SOL 현물 `change 5% 1h` 양방향 |
| `volume-burst` | 거래량 폭발 | BTC·ETH·SOL·XRP·BNB 현물 `volume x3 5m/1h` |
| `futures-heat` | 선물 과열 | f:BTC·f:ETH `funding above 0.05%`, `funding below -0.05%` |

프리셋은 `src/presets/*.json`에 규칙 목록으로 정의하고, 설치하면 규칙이 `source: preset:<슬러그>`로 복사된다. 제거하면 해당 출처의 규칙만 삭제한다.

**외부 프리셋 (v1.2, D-101~D-109):** 파일 또는 https 주소로 설치하는 프리셋은 아래 형식이며, 설치 전에 모두 검증한다. 규칙은 모두 `source: preset:<슬러그>`로 저장한다.

```json
{ "schemaVersion": 1, "slug": "my-preset", "version": 1, "name": "내 프리셋", "license": "CC0-1.0",
  "rules": [ { "type": "price", "market": "futures", "symbol": "BTCUSDT",
               "condition": { "type": "price", "direction": "above", "price": 84500 },
               "repeat": { "kind": "cooldown", "ms": 300000 } } ] }
```

### 평가 순서

1. 이벤트가 들어오면 같은 시장·심볼의 활성 규칙만 골라 평가한다.
2. 조건을 만족하면 반복 정책을 확인해 발동 여부를 정한다.
3. 발동한 알림은 모두 notify로 넘기고, 묶음 처리는 notify가 한다 (B7).
4. 상태(`RuleState`)를 갱신해 저장한다.

## B5. 바이낸스 연동

공개 시장 데이터는 사용자 수와 무관하게 필요한 스트림만 한 번 구독하고, 계정 데이터는 WebSocket API의 사용자 데이터 스트림 구독 방식을 쓴다. listenKey 기반 방식은 바이낸스가 퇴출 중이므로 사용하지 않는다 (D-06).

| 연결 | 용도 | 인증 | 버전 |
| --- | --- | --- | --- |

## B6. 보안 설계

키는 OS 키체인에만 저장하고, 거래·출금 권한이 하나라도 켜진 키로는 어떤 계정 기능도 동작하지 않는다. 로컬 저장은 서버 유출을 없애지만 PC 악성코드와 npm 공급망 공격은 남으므로 아래 대책을 함께 적용한다.

| 위협 | 대책 | 요구사항 |
| --- | --- | --- |
| 평문 설정 파일 유출 | 키·시크릿은 OS 키체인에만 저장, 설정 파일에는 참조 이름만 | FR-KEY-01, NFR-SEC-01 |
| 과도한 키 권한 | 시작 시와 재연결 시도마다 권한을 조회해 허용 목록 밖의 권한이 켜져 있으면(D-41) 실행 거부 | FR-KEY-02, FR-KEY-04 |

### 권한 검사 흐름

1. 키체인에서 키를 읽는다.
2. 바이낸스에 키 권한 설정을 조회한다.
3. 거래·출금 권한이 켜져 있으면 어떤 권한이 문제인지와 바이낸스에서 끄는 방법을 안내하고 종료 코드 2로 끝낸다.
4. IP 제한이 없으면 경고를 표시하고 계속한다.
5. 권한 조회는 BLERT_NETWORK=testnet에서는 건너뛴다(D-39). 재연결할 때마다 2\~4를 반복한다. 실행 중 권한 초과가 발견되면 계정 기능만 멈추고 공개 알림은 유지한다.

### 키체인을 쓸 수 없는 환경 (D-30)

일부 Linux처럼 키체인이 없으면 `blert key add`를 거부하고 계정 기능을 비활성화한다. 공개 알림은 정상 동작하며, 시작할 때 한 번 안내한다. 환경변수·평문 파일로의 대체 저장은 제공하지 않는다.

## B7. 알림 출력

출력은 채널 어댑터 구조로 만든다. v0.1은 데스크톱 알림과 사운드 두 어댑터만 구현하되, 텔레그램 등은 어댑터 하나를 추가하는 것으로 붙을 수 있어야 한다 (FR-NOTI-03).

| 어댑터 | 역할 | 버전 | 실패 시 |
| --- | --- | --- | --- |
| desktop | OS 기본 알림 표시 | v0.1 | console로 대체 + 알림 권한 설정 안내 |
| sound | 알림 유형별 음원 재생 | v0.1 | 무음으로 계속 + 1회 경고 |
| console | 포그라운드 실행 시 터미널 출력 | v0.1 | — |
| telegram | 외부 채널(텔레그램 봇, D-69~D-73) | v1.0 | 재시도 후 포기, 데스크톱·소리에 영향 없음, 안내 1회 |

### 어댑터 인터페이스 (초안)

```ts
interface Alert {
  ruleId: number;
  kind: 'up' | 'down' | 'account' | 'warn';  // 사운드·아이콘 선택 기준
  titleKey: string;                          // i18n 메시지 키 (본문 키는 .title → .body)
  params: Record<string, string | number>;   // market(spot/futures)과 이름이 Ms로 끝나는 기간(ms)은 notify가 한글로 바꾼다 (engine은 i18n에 의존하지 않는다)
  firedAt: string;
  sound?: 'up' | 'down' | 'account' | 'warn' | 'off';  // 규칙의 --sound 지정. 없으면 kind를 따르고 'off'면 무음
}

interface NotifyAdapter {
  name: string;
  send(alerts: Alert[]): Promise<void>;      // 묶음 단위로 전달
}
```

### 사운드 매핑 (D-29)

사용자가 소리를 등록하면(D-81~D-83) 그 종류는 사용자 소리를 먼저 재생한다. 등록이 없거나 파일이 없거나 재생할 수 없으면 아래 번들 소리로 대신 재생하고 경고를 한 번만 안내한다(D-98). 소리는 재생할 때마다 설정을 읽어 바로 반영한다(D-95). 설치 전 검사 기준은 D-92다.

**음성 알림 (v1.3, D-110~D-117):** `voice on`이면 읽을 종류(`kinds`, 기본 `warn`·`account`)의 알림을 소리가 끝난 뒤에 OS 내장 TTS로 읽는다. 읽을 문장은 화면 제목이 아니라 `speech.*` 키의 짧은 문장이다. 재생은 한 번에 하나이고 대기 2건을 넘으면 오래된 것을 버린다. 문장은 환경 변수로만 전달하고 설정은 재생할 때마다 읽는다. 선택한 음성이 없으면 OS 기본 음성으로 대신하고 경고를 한 번만 안내한다.

**조용한 시간 (v1.5, D-135~D-141):** `snooze` 또는 `quiet`가 켜져 있으면 알림을 보낼 때마다 설정을 읽어 판정한다. 기본은 소리·음성 어댑터만 건너뛰고 화면 알림은 그대로 보낸다. `--all`이면 화면과 외부 채널 어댑터도 건너뛴다. warn 종류는 `--include-warn`이 없으면 조용한 시간에도 정상으로 보낸다. 건너뛴 알림도 기록 어댑터에는 전달하며 `quiet` 표시가 붙는다. 판정 함수와 기록 쓰기는 `src/index.ts`에서 주입한다(B2).

| 종류 | 쓰이는 알림 | 소리 성격 | 파일 |
| --- | --- | --- | --- |
| up | 가격 상향 돌파, 상승 변동, 거래량 급증 | 밝고 올라가는 짧은 음 | `assets/sounds/up.wav` |
| down | 가격 하향 돌파, 하락 변동 | 낮고 내려가는 짧은 음 | `assets/sounds/down.wav` |
| account | 체결, 잔고 변동 | 부드러운 코인·벨 소리 | `assets/sounds/account.wav` |
| warn | 청산가 근접, 펀딩비 과열, 연결 끊김, 절전 복귀 | 반복되는 경고음, 다른 셋과 확실히 구분 | `assets/sounds/warn.wav` |

**음원 선정 기준 (10월 4일 작업):** CC0 라이선스(출처 표기 의무 없음)를 우선한다. 후보 출처는 Kenney 에셋 팩과 Freesound의 CC0 필터 검색이다. 길이 1.5초 이하, 파일당 100KB 이하, 형식은 WAV로 통일한다. WAV는 macOS·Windows·Linux 기본 재생 도구가 모두 지원해 추가 의존성이 필요 없다. 선정한 파일의 출처 URL과 라이선스는 `assets/sounds/LICENSES.md`에 기록한다 (NFR-LEGAL-02).

### 알림 폭주 묶음 (D-28)

- 알림 지연 1초 이내(NFR-PERF-01)를 지키기 위해 비(非) warn 알림은 0.3초 동안 모은 뒤 보낸다. 모인 알림이 3건 이상이면 "알림 N건" 요약 1건으로 보내고 사운드는 한 번만 재생한다. 10초 창에서 이미 2건이 나간 뒤 2건 이상 모이면 그것도 묶는다.
- 요약 알림에는 상위 3건의 제목을 보여주고, 전체는 콘솔과 로그에 남긴다.
- warn 종류는 묶지 않고 항상 개별로 보낸다.

## B9. 실행 모드

세 모드는 같은 감시 코어를 공유하고, 감시 코어를 띄우는 방식만 다르다. 그래야 v0.4·v0.5에서 코어를 다시 짜지 않는다.

| 모드 | 명령 | 버전 | 요구사항 | 동작 |
| --- | --- | --- | --- | --- |
| 포그라운드 | `run` | v0.1 | FR-RUN-01 | 현재 터미널에서 감시 코어 실행, console 어댑터 켜짐, PID 파일로 중복 실행 방지 |
| 백그라운드 데몬 | `start` / `stop` / `status` / `logs` | v0.4 | FR-RUN-03 | 같은 실행 파일을 숨김 내부 명령으로 분리 실행(D-54), 알림은 desktop·sound 어댑터(D-55), `start`는 준비 완료를 최대 15초 기다려 결과를 보고(D-58), `stop`은 요청 파일로 정상 종료(D-57), PID 파일로 중복 실행 방지 |
| OS 서비스 | `service install` / `uninstall` | v0.5 | FR-RUN-04 | Windows 작업 스케줄러 로그온 작업(D-62~D-66). 서비스로 시작하면 연결 실패에도 종료하지 않고 재시도(D-67), 이미 실행 중이면 조용히 종료(D-68). macOS launchd·Linux systemd는 v0.5 범위 밖(D-63, Q-12) |

### 절전 복귀 감지 (모든 모드 공통, v0.1)

15초마다 시계를 확인해 직전 확인보다 60초 이상 흘렀으면 절전 복귀로 판단한다. 이때 모든 연결을 재연결하고, 감시가 멈췄던 시작·종료 시각을 warn 알림으로 보낸다 (FR-RUN-02, NFR-REL-02).

### 시작과 종료

1. 시작: 설정 로드 → 스키마 확인·마이그레이션 → 고지 동의 확인(D-36) → 실행 잠금(`blert.pid`, D-35) → (키가 있으면) 권한 검사 → 스트림 연결 → 감시 시작 알림.
2. 종료(Ctrl+C, `stop`, 종료 신호): 새 이벤트 수신 중단 → 상태 저장 → 연결 종료 → PID 파일 삭제.
3. 이미 실행 중일 때 `run`이나 `start`를 하면 거부한다. 포그라운드는 실행 중인 터미널에서 Ctrl+C로 종료하라고, 데몬(v0.4)은 `blert status`를 안내한다.
4. 필요한 시장 중 일부만 연결되면 시작하되, 감시하지 못하는 규칙 수를 warn 알림과 콘솔로 알리고 계속 재시도한다. 복구되면 알린다 (D-37).
5. 이전 실행의 `blert.pid`가 남아 있고 주인이 없으면(프로세스가 없거나 생존 신호가 60초 넘게 끊김) 그 구간을 감시 중단 알림으로 알린다 (D-35).

## B10. 오류 처리·로깅

원칙은 하나다. 감시가 멈추거나 알림을 못 보낼 수 있는 상황은 조용히 넘기지 않고 반드시 사용자에게 알린다.

| 오류 분류 | 예시 | 처리 | 종료 코드 |
| --- | --- | --- | --- |
| 사용자 입력 오류 | 잘못된 심볼, 문법 오류 | 원인 + 올바른 예시 + 오타 제안 | 1 |
| 권한 오류 | 거래·출금 권한 켜진 키, HMAC 키 | 실행 거부 + 바이낸스에서 고치는 방법 안내 | 2 |
| 연결 오류 | 네트워크 끊김, 24시간 만료 | 자동 재연결, 5분 초과 시 warn 알림 | 3 (시작할 때 필요한 시장이 모두 연결 불가일 때만. 일부만 실패하면 계속 실행) |
| 외부 API 오류 | 레이트 리밋, 점검 | 대기 후 재시도, 반복되면 경고 | — |
| 출력 오류 | 알림 권한 없음, 사운드 재생 실패 | console로 대체 + 1회 경고 | — |
| 내부 오류 | 예상 못한 예외 | 로그 기록 후 감시 코어 재시작, 3회 연속이면 종료 | 9 |

### 메시지와 로그 규칙

- 사용자 메시지는 "무엇이 문제인지 + 어떻게 고치는지 + 예시" 3요소를 갖추고, 모두 i18n 키로 관리한다 (NFR-UX-02, NFR-UX-03).
- 로그 레벨은 error, warn, info, debug 4단계. 기본은 info, `--verbose`로 debug.
- 로그는 한 줄에 한 이벤트, 시각·레벨·모듈·메시지 순서. 키 형태 문자열은 기록 전에 마스킹한다.

# Part C. 구현 지침

## C. Claude Code 구현 지침

Claude Code는 이 절을 작업 규칙으로 따른다. `CLAUDE.md`에 그대로 옮겨도 된다.

### 작업 규칙

1. 지시받은 버전의 요구사항만 구현한다. 다음 버전 기능을 미리 만들지 않는다.
2. A6 범위 밖 항목은 구현하지도, 제안하지도 않는다.
3. 문서에 없는 결정이 필요하면 임의로 정하지 말고 질문으로 남긴다.
4. 설계와 다르게 구현해야 할 이유가 생기면 먼저 알리고 승인을 받는다.
5. 키·시크릿을 코드, 로그, 테스트 데이터, 커밋에 절대 넣지 않는다.
6. 새 의존성을 추가할 때는 이유를 적고 승인을 받는다.
7. 바이낸스 API 명칭은 구현 시점의 공식 문서로 확인한다.
