## 문서 안내

이 문서는 Claude Code가 그대로 읽고 구현할 수 있도록 만든 blert의 기획서와 설계서다. v0.1과 v0.2 구현에 필요한 내용은 모두 채워져 있고, v0.3 이후 항목은 해당 버전 착수 전에 보강한다.

### 기획 범위와 설계 범위

| 구분 | 답하는 질문 | 담는 내용 | 누가 주로 읽나 |
| --- | --- | --- | --- |
| 기획서 (Part A) | 무엇을, 왜 만드는가 | 서비스 정의, 사용자, 결정사항, 기능·비기능 요구사항, 범위 밖, 로드맵, 미결 사항 | 기획자(본인), Claude Code의 작업 판단 기준 |
| 설계서 (Part B) | 어떻게 만드는가 | 구조, 모듈, 명령어 명세, 데이터 모델, 외부 연동, 보안, 실행 모드, 테스트 | Claude Code의 구현 입력 |
| 구현 지침 (Part C) | 어떤 순서와 규칙으로 만드는가 | 단계별 작업 순서, 코딩 규칙, 완료 보고 방식 | Claude Code |

# Part A. 기획서

## A1. 서비스 개요

**한 줄 정의:** 명령어 한 줄로 설치하고, 명령어 몇 개로 바이낸스 현물·선물 알림을 설정해 내 PC에서 데스크톱 알림과 소리로 받는 로컬 CLI 도구.

| 항목 | 내용 |
| --- | --- |
| 서비스 이름 | `blert` (binance + alert). npm 패키지명·명령어 동일 |
| 모티브 | [sounds.sh](https://www.sounds.sh/) — 한 줄 설치, 큐레이션된 테마 묶음, 터미널을 들여다보지 않아도 되는 알림 |
| 형태 | TypeScript + Node.js CLI, npm 배포 (`npx blert ...`) |
| 실행 위치 | 사용자 PC (서버 없음) |
| 핵심 가치 1 | 한 줄 설치 + 프리셋 한 줄로 바로 쓸 수 있음 |
| 핵심 가치 2 | 키와 데이터가 사용자 PC 밖으로 나가지 않음 |
| 핵심 가치 3 | 읽기 전용 키만 허용해 최악의 경우에도 자산 이동이 불가능함 |

### sounds.sh 대응표

| sounds.sh | blert |
| --- | --- |
| `npx soundsh find` 한 줄 설치 | `npx blert init` |
| 테마 (이벤트 사운드 묶음) | 프리셋 (알림 조건 묶음) |
| 테마 단일 명령 설치 | `blert preset install <이름>` |
| 이벤트별 사운드 | 알림 유형별 사운드 (저작권 없는 음원) |
| 웹 갤러리 | v1.0 프리셋 갤러리 |

## A2. 대상 사용자와 사용 시나리오

주 사용자는 PC 앞에서 작업하면서 바이낸스 시세나 자기 계정 상태를 놓치고 싶지 않은 개발자·트레이더다. 터미널 사용에 익숙하다고 가정한다.

| 사용자 유형 | 특징 | 주로 쓰는 기능 |
| --- | --- | --- |
| 입문 사용자 | 명령어 문법을 모름, 기본값을 그대로 씀 | `init`, 프리셋 |
| 일반 사용자 | 코인별로 원하는 조건이 있음 | 개별 알림 추가·삭제 |
| 고급 사용자 | 반복 정책까지 직접 조정 | `--mode` 등 고급 옵션 |

### 대표 시나리오

| ID | 시나리오 | 목표 버전 |
| --- | --- | --- |
| SC-01 | 처음 설치하고 프리셋 하나로 1분 안에 첫 알림을 받는다 | v0.1 |
| SC-02 | BTC 목표가 알림을 추가하고, 도달하면 소리와 함께 알림을 받는다 | v0.1 |
| SC-03 | 노트북 절전 후 복귀했을 때 감시 중단 구간을 안내받는다 | v0.1 |
| SC-04 | 읽기 전용 키를 등록하고 내 주문 체결 알림을 받는다 | v0.2 |
| SC-05 | 거래 권한이 켜진 키를 등록하려다 거부 안내를 받는다 | v0.2 |
| SC-06 | 선물 포지션 청산가 근접 알림을 받는다 | v0.3 |
| SC-07 | 터미널을 닫아도 백그라운드에서 감시가 계속된다 | v0.4 |

### 시나리오별 단계 흐름

| ID | 사용자 행동 | 시스템 반응 | 성공 기준 |
| --- | --- | --- | --- |
| SC-01 | `npx blert init` → 고지 동의 → 사운드 켜기 → 프리셋 `major-swing` 선택 → `blert run` | 설정 폴더 생성, 규칙 3개 등록, 감시 시작 알림 표시 | 설치부터 감시 시작 알림까지 1분 이내 |
| SC-02 | `blert add price BTC above 70000` → `blert run` | 규칙 등록 확인 메시지. 가격 돌파 시 데스크톱 알림 + up 사운드, 규칙은 1회성으로 비활성 | `list --all`에서 비활성 상태로 보임 |
| SC-03 | `run` 중 노트북 덮개를 닫았다가 연다 | 60초 이상 공백 감지 → 재연결 → "감시 중단: 시작\~종료 시각" warn 알림 | 공백 구간이 알림과 로그에 남음 |
| SC-04 | `blert key add` → Ed25519 키 입력 → `blert add fill all` → `blert run` | 키체인 저장, 권한 검사 통과, 체결 시 account 사운드와 알림 | 설정 파일·로그에 키 흔적 0건 |
| SC-05 | 거래 권한이 켜진 키로 `blert key add` | 어떤 권한이 문제인지와 끄는 방법 안내, 저장하지 않음, 종료 코드 2 | 키가 키체인에 남지 않음 |
| SC-06 | `blert add liq f:BTC 5%` → `blert run` | 청산가까지 거리가 5% 이하가 되면 warn 알림, 5분 쿨다운 | Q-01 결과에 따라 흐름 확정 |
| SC-07 | `blert start` → 터미널 종료 → `blert status` | 데몬이 계속 실행되며 status가 실행 중과 규칙 수를 표시 | 터미널을 닫은 뒤에도 알림 수신 |

# Part B. 설계서

## B1. 시스템 구조 개요

모든 모듈은 사용자 PC의 한 프로세스 안에서 돌고, 네트워크로 나가는 곳은 바이낸스뿐이다. 판단은 engine 한 곳에서만 한다.

&#91;embedded content: 모듈 구조 · 외부 통신은 바이낸스 한 곳\]

사용자 명령은 cli를 거쳐 store에 규칙으로 저장되고, binance 모듈이 받은 이벤트를 engine이 규칙과 대조해 notify로 내보낸다. runtime은 이 모듈들을 조립하고 실행 모드와 재연결을 맡는다.

## B2. 디렉터리·모듈 구조

모듈은 책임 하나씩만 가진다. 바이낸스 연동, 규칙 판단, 출력은 서로 직접 부르지 않고 이벤트로만 주고받는다. 코드는 TypeScript(strict)로 작성하고 `dist/`로 빌드해 배포한다.

```text
blert/
├─ src/
│  ├─ index.ts      진입점 (bin)
│  ├─ cli/          명령어 파싱, 도움말, 입력 검증, 오타 제안
│  ├─ presets/      프리셋 정의(JSON)와 설치·제거
│  ├─ engine/       알림 규칙 평가, 반복 정책, 폭주 묶음
│  ├─ binance/      공개 스트림, 사용자 데이터 스트림, REST 보충 조회
│  ├─ security/     키체인 저장, 권한 검사
│  ├─ notify/       데스크톱 알림, 사운드, 콘솔, 채널 어댑터
│  ├─ store/        설정·규칙·상태 JSON 저장, 파일 잠금
│  ├─ runtime/      실행 모드, 절전 감지, 생명주기
│  ├─ i18n/         메시지 파일 (ko.json)
│  └─ shared/       로깅, 오류 타입, 공통 유틸, 타입 정의
├─ assets/sounds/   저작권 없는 음원 + LICENSES.md
├─ docs/            이 기획서·설계서
├─ test/
├─ package.json
└─ tsconfig.json
```

| 모듈 | 책임 | 의존 가능 | 첫 버전 |
| --- | --- | --- | --- |
| cli | 사용자 입력을 명령 객체로 변환 | store, presets, security, i18n | v0.1 |
| presets | 프리셋 → 알림 규칙 목록 변환 | store | v0.1 |
| engine | 시장·계정 이벤트를 규칙과 대조, 발동 결정 | store | v0.1 |
| binance | 바이낸스 연결과 이벤트 발행 | security | v0.1 |
| security | 키 보관·권한 검사 | — | v0.2 |
| notify | 발동된 알림을 채널로 출력 | i18n | v0.1 |
| store | 설정 파일과 알림 상태 읽기·쓰기 | — | v0.1 |
| i18n | 메시지 키 → 한국어 문장 변환 | — | v0.1 |
| runtime | 모듈 조립, 실행 모드, 재시작 | 전체 | v0.1 |

### 모듈 간 이벤트

모듈은 runtime이 만든 타입 있는 이벤트 버스 하나로만 통신한다. 모든 이벤트는 `ts`(ISO 8601)를 가진다.

| 이벤트 | 발행 | 구독 | 내용 | 버전 |
| --- | --- | --- | --- | --- |
| `market.ticker` | binance | engine | market, symbol, price, quoteVolume | v0.1 |
| `market.kline` | binance | engine | market, symbol, openTime, close, quoteVolume, closed (1분봉. 백필 데이터도 같은 이벤트로 발행) | v0.1 |
| `market.funding` | binance | engine | symbol, rate, nextFundingTime | v0.1 |
| `account.fill` | binance | engine | market, symbol, side, qty, price, orderId | v0.2 |
| `account.balance` | binance | engine | asset, free, locked | v0.2 |
| `account.position` | binance | engine | symbol, side, size, entryPrice, liqPrice | v0.3 |
| `rule.fired` | engine | notify | B7의 `Alert` | v0.1 |
| `rules.changed` | store | binance, engine | 바뀐 규칙 ID 목록 (구독 목록 갱신용) | v0.1 |
| `conn.status` | binance | runtime, notify | stream, state(connecting·open·retrying·closed), attempt | v0.1 |
| `conn.gap` | runtime, binance | notify | from, to, reason(sleep·disconnect) | v0.1 |
| `key.denied` | security | runtime, notify | reason(trade·withdraw·hmac·no-keychain) | v0.2 |

```ts
type BlertEvent =
  | { type: 'market.ticker'; ts: string; market: Market; symbol: string; price: number; quoteVolume: number }
  | { type: 'market.kline'; ts: string; market: Market; symbol: string; openTime: string; close: number; quoteVolume: number; closed: boolean }
  | { type: 'market.funding'; ts: string; symbol: string; rate: number; nextFundingTime: string }
  | { type: 'rule.fired'; ts: string; alert: Alert }
  | { type: 'rules.changed'; ts: string; ruleIds: number[] }
  | { type: 'conn.status'; ts: string; stream: string; state: 'connecting' | 'open' | 'retrying' | 'closed'; attempt: number }
  | { type: 'conn.gap'; ts: string; from: string; to: string; reason: 'sleep' | 'disconnect' };
  // v0.2 이후 이벤트는 해당 버전에서 추가
```

데몬 모드(v0.4)에서는 CLI와 데몬이 다른 프로세스이므로, CLI가 `rules.json`을 쓰면 데몬이 파일 변경을 감지해 `rules.changed`를 발행한다.

## B3. CLI 명령어 명세

명령은 `blert <동사> <대상> <인자>` 순서의 단어형이다 (D-19). 셸 특수문자(`>`, `<`, `|`)는 문법에 쓰지 않는다.

- `list`는 ID, 상태, 유형, 시장, 심볼, 조건, 반복 정책, 출처 열의 표로 출력한다.
- 명령·유형·옵션의 철자가 2글자 이내로 다르면 "혹시 `<제안>`?"을 보여준다 (FR-CLI-03).
- 모든 명령의 `--help`에 사용 예를 최소 2개 넣는다 (FR-CLI-04).

| 종료 코드 | 의미 |
| --- | --- |
| 0 | 성공 |
| 1 | 입력 오류 |
| 2 | 권한 거부 (키 권한 초과 등) |
| 3 | 연결 실패 |
| 9 | 내부 오류 |

## B4. 알림 모델과 규칙 엔진

모든 알림은 하나의 규칙(Rule) 형식으로 저장된다. 명령어로 만든 알림과 프리셋으로 설치한 알림은 같은 형식이며, 엔진은 출처를 구분하지 않는다.

### 규칙 타입 (초안)

```ts
type Market = 'spot' | 'futures';
type RepeatPolicy =
  | { kind: 'once' }
  | { kind: 'cooldown'; ms: number }          // 1분 ~ 24시간
  | { kind: 'hysteresis'; widthPct: number }; // 기준값 대비 %

interface Rule {
  id: number;
  type: 'price' | 'change' | 'volume' | 'funding' | 'fill' | 'balance' | 'liq';
  market: Market;
  symbol: string;            // 정규화된 전체 심볼, 예: BTCUSDT
  condition: Condition;      // 유형별 조건 (아래 표)
  repeat: RepeatPolicy;
  sound?: 'up' | 'down' | 'account' | 'warn' | 'off';
  name?: string;
  source: 'manual' | `preset:${string}`;
  enabled: boolean;
  createdAt: string;         // ISO 8601
}

interface RuleState {        // 규칙과 분리해 저장 (B8)
  ruleId: number;
  lastFiredAt?: string;
  armed: boolean;            // 히스테리시스 재무장 여부
}
```

### 유형별 조건

| 유형 | 조건 | 판정 방식 | 근거 |
| --- | --- | --- | --- |
| price | 방향(above/below), 가격 | 현재가가 기준을 넘는 순간 | FR-ALERT-01 |
| change | 퍼센트, 기간, 방향 | 롤링 윈도우: 현재가를 (현재 − 기간) 시점 가격과 비교. 기간만큼의 가격 이력을 메모리에 유지 | D-24 |
| volume | 배수, 짧은 구간, 긴 구간 | 짧은 구간 거래대금 ÷ (긴 구간 거래대금을 짧은 구간 단위로 나눈 평균) ≥ 배수 | D-25 |
| funding | 방향, 퍼센트 | 예상 펀딩비가 기준을 넘는 순간 | FR-ALERT-04 |
| fill | 심볼 또는 all | 주문 체결 이벤트 수신 시 | FR-ACC-01 |
| balance | 자산, 퍼센트 | 마지막 알림 시점 대비 잔고가 퍼센트 이상 변동 | D-27 |
| liq | 퍼센트 | 현재가와 청산가 거리가 퍼센트 이하 (Q-01 결과 반영) | FR-ALERT-05 |

### 알림 유형별 기본 반복 정책

| 유형 | 기본 정책 | 버전 |
| --- | --- | --- |
| price | 1회성 | v0.1 |
| change | 쿨다운 30분 | v0.1 |
| volume | 쿨다운 15분 | v0.1 |
| funding | 히스테리시스, 폭 20% | v0.1 |
| fill | 이벤트마다 1회 (반복 정책 없음) | v0.2 |
| balance | 쿨다운 10분 | v0.2 |
| liq | 쿨다운 5분 | v0.3 |

### 반복 정책 동작

| 정책 | 동작 | 기본값·범위 |
| --- | --- | --- |
| 1회성 | 발동 후 `enabled=false`. 삭제하지 않고 보관, `list --all`로 확인 | — |
| 쿨다운 | 발동 후 지정 시간 동안 재발동 금지 | 1분 \~ 24시간 |
| 히스테리시스 | 발동 후 `armed=false`. 값이 기준에서 폭(기준값 대비 %)만큼 반대로 벗어나면 `armed=true`로 재무장 | 가격류 0.5%, 펀딩비 20% |

### 기본 프리셋 (D-23)

| 슬러그 | 표시 이름 | 포함 규칙 |
| --- | --- | --- |
| `major-swing` | 메이저 급등락 | BTC·ETH·SOL 현물 `change 5% 1h` 양방향 |
| `volume-burst` | 거래량 폭발 | BTC·ETH·SOL·XRP·BNB 현물 `volume x3 5m/1h` |
| `futures-heat` | 선물 과열 | f:BTC·f:ETH `funding above 0.05%`, `funding below -0.05%` |

프리셋은 `src/presets/*.json`에 규칙 목록으로 정의하고, 설치하면 규칙이 `source: preset:<슬러그>`로 복사된다. 제거하면 해당 출처의 규칙만 삭제한다.

### 평가 순서

1. 이벤트가 들어오면 같은 시장·심볼의 활성 규칙만 골라 평가한다.
2. 조건을 만족하면 반복 정책을 확인해 발동 여부를 정한다.
3. 발동한 알림은 모두 notify로 넘기고, 묶음 처리는 notify가 한다 (B7).
4. 상태(`RuleState`)를 갱신해 저장한다.

## B5. 바이낸스 연동

공개 시장 데이터는 사용자 수와 무관하게 필요한 스트림만 한 번 구독하고, 계정 데이터는 WebSocket API의 사용자 데이터 스트림 구독 방식을 쓴다. listenKey 기반 방식은 바이낸스가 퇴출 중이므로 사용하지 않는다 (D-06).

| 연결 | 용도 | 인증 | 버전 |
| --- | --- | --- | --- |
| 현물 공개 스트림 | 가격(티커), 변동률·거래량(1분봉 `kline_1m`) | 없음 | v0.1 |
| 선물 공개 스트림 | 가격(티커), 변동률·거래량(1분봉 `kline_1m`), 펀딩비 | 없음 | v0.1 |
| 현물 WebSocket API 사용자 데이터 | 체결, 잔고 | Ed25519 서명 (D-16) | v0.2 |
| 선물 사용자 데이터 | 포지션, 주문 | Ed25519, 방식은 Q-01 결과에 따름 | v0.3 |
| REST | 권한 검사, 재연결 후 보충 조회 | Ed25519 서명 | v0.2 |

### 연결 생명주기

| 상황 | 동작 | 값 |
| --- | --- | --- |
| 24시간 연결 만료 | 만료 전에 새 연결을 열고 옮긴 뒤 기존 연결 종료 | 만료 10분 전 |
| 시작·재연결 직후 (공개) | 변동률·거래량 규칙에 필요한 구간(최대 24시간 + 여유 2분)의 1분봉을 REST로 백필하고 이후 스트림으로 이어 붙인다 (D-33) | 규칙이 필요로 하는 최대 구간 |
| 연결 끊김 | 지수 백오프로 무한 재시도, 상태를 콘솔에 표시 | 1초 → 최대 60초 |
| 장시간 끊김 | 사용자에게 경고 알림 | 5분 초과 시 |
| 재연결 후 (계정) | 끊긴 구간의 체결·잔고를 REST로 보충 조회 | v0.2 |
| 규칙 변경 | 필요한 심볼만 구독하도록 구독 목록 갱신 | 즉시 |
| 레이트 리밋 응답 | 응답의 대기 시간만큼 멈춘 뒤 재시도, 반복되면 경고 | — |

### 구현 시 확인할 것

- 스트림·메서드 이름은 구현 시점의 바이낸스 공식 문서로 확인하고 코드 주석에 문서 링크를 남긴다.
- 계정 기능 테스트는 바이낸스 테스트넷으로만 한다 (B11).

## B6. 보안 설계

키는 OS 키체인에만 저장하고, 거래·출금 권한이 하나라도 켜진 키로는 어떤 계정 기능도 동작하지 않는다. 로컬 저장은 서버 유출을 없애지만 PC 악성코드와 npm 공급망 공격은 남으므로 아래 대책을 함께 적용한다.

| 위협 | 대책 | 요구사항 |
| --- | --- | --- |
| 평문 설정 파일 유출 | 키·시크릿은 OS 키체인에만 저장, 설정 파일에는 참조 이름만 | FR-KEY-01, NFR-SEC-01 |
| 과도한 키 권한 | 시작 시와 재연결 시 권한을 조회해 거래·출금 권한이 있으면 실행 거부 | FR-KEY-02, FR-KEY-04 |
| IP 제한 없는 키 | 실행은 허용하되 매번 경고 | FR-KEY-03 |
| 약한 키 방식 | Ed25519 키만 등록 허용, HMAC 키는 등록 단계에서 거부하고 생성 방법 안내 | D-16 |
| 로그·오류 메시지 노출 | 로거에서 키 형태 문자열 마스킹 | NFR-SEC-01 |
| npm 공급망 공격 | 의존성 10개 이하·버전 고정, provenance 서명, 전역 설치 + 버전 고정 안내 | NFR-SEC-03, NFR-SEC-04 |
| 외부 전송 | 바이낸스 외 네트워크 요청 금지 | NFR-SEC-02 |

### 권한 검사 흐름

1. 키체인에서 키를 읽는다.
2. 바이낸스에 키 권한 설정을 조회한다.
3. 거래·출금 권한이 켜져 있으면 어떤 권한이 문제인지와 바이낸스에서 끄는 방법을 안내하고 종료 코드 2로 끝낸다.
4. IP 제한이 없으면 경고를 표시하고 계속한다.
5. 재연결할 때마다 2\~4를 반복한다. 실행 중 권한 초과가 발견되면 계정 기능만 멈추고 공개 알림은 유지한다.

### 키체인을 쓸 수 없는 환경 (D-30)

일부 Linux처럼 키체인이 없으면 `blert key add`를 거부하고 계정 기능을 비활성화한다. 공개 알림은 정상 동작하며, 시작할 때 한 번 안내한다. 환경변수·평문 파일로의 대체 저장은 제공하지 않는다.

### 구현 시 정할 것

- [ ] 키체인 라이브러리 선정 (유지보수 상태 확인, 의존성 승인 필요)
- [ ] 허용 권한 목록의 정확한 정의 (Q-01 결과 반영)

## B7. 알림 출력

출력은 채널 어댑터 구조로 만든다. v0.1은 데스크톱 알림과 사운드 두 어댑터만 구현하되, 텔레그램 등은 어댑터 하나를 추가하는 것으로 붙을 수 있어야 한다 (FR-NOTI-03).

| 어댑터 | 역할 | 버전 | 실패 시 |
| --- | --- | --- | --- |
| desktop | OS 기본 알림 표시 | v0.1 | console로 대체 + 알림 권한 설정 안내 |
| sound | 알림 유형별 음원 재생 | v0.1 | 무음으로 계속 + 1회 경고 |
| console | 포그라운드 실행 시 터미널 출력 | v0.1 | — |
| telegram 등 | 외부 채널 | v1.0 | — |

### 어댑터 인터페이스 (초안)

```ts
interface Alert {
  ruleId: number;
  kind: 'up' | 'down' | 'account' | 'warn';  // 사운드·아이콘 선택 기준
  titleKey: string;                          // i18n 메시지 키
  params: Record<string, string | number>;
  firedAt: string;
}

interface NotifyAdapter {
  name: string;
  send(alerts: Alert[]): Promise<void>;      // 묶음 단위로 전달
}
```

### 사운드 매핑 (D-29)

| 종류 | 쓰이는 알림 | 소리 성격 | 파일 |
| --- | --- | --- | --- |
| up | 가격 상향 돌파, 상승 변동, 거래량 급증 | 밝고 올라가는 짧은 음 | `assets/sounds/up.wav` |
| down | 가격 하향 돌파, 하락 변동 | 낮고 내려가는 짧은 음 | `assets/sounds/down.wav` |
| account | 체결, 잔고 변동 | 부드러운 코인·벨 소리 | `assets/sounds/account.wav` |
| warn | 청산가 근접, 펀딩비 과열, 연결 끊김, 절전 복귀 | 반복되는 경고음, 다른 셋과 확실히 구분 | `assets/sounds/warn.wav` |

**음원 선정 기준 (10월 4일 작업):** CC0 라이선스(출처 표기 의무 없음)를 우선한다. 후보 출처는 Kenney 에셋 팩과 Freesound의 CC0 필터 검색이다. 길이 1.5초 이하, 파일당 100KB 이하, 형식은 WAV로 통일한다. WAV는 macOS·Windows·Linux 기본 재생 도구가 모두 지원해 추가 의존성이 필요 없다. 선정한 파일의 출처 URL과 라이선스는 `assets/sounds/LICENSES.md`에 기록한다 (NFR-LEGAL-02).

### 알림 폭주 묶음 (D-28)

- 10초 창 안에 발동한 알림이 3건 이상이면 "알림 N건" 요약 1건으로 보내고, 사운드는 한 번만 재생한다.
- 요약 알림에는 상위 3건의 제목을 보여주고, 전체는 콘솔과 로그에 남긴다.
- warn 종류는 묶지 않고 항상 개별로 보낸다.

### 메시지 형식

| 유형 | 제목 예 | 본문 예 | 사운드 |
| --- | --- | --- | --- |
| price (상향) | BTC 70,000 돌파 | 현재 70,012 USDT · 현물 | up |
| price (하향) | BTC 65,000 이탈 | 현재 64,980 USDT · 현물 | down |
| change | ETH 1시간 −5.2% | 3,412 → 3,235 USDT · 현물 | up / down |
| volume | SOL 거래량 4.1배 급증 | 5분 거래대금 12.3M USDT (1시간 평균 3.0M) | up |
| funding | BTC 선물 펀딩비 0.061% | 기준 0.05% 초과 | warn |
| fill | BTC 매수 체결 | 0.015 BTC @ 68,420 USDT | account |
| balance | USDT 잔고 −12.4% | 5,210 → 4,564 USDT | account |
| liq | BTC 청산가까지 4.8% | 현재 66,100 · 청산가 62,930 USDT | warn |
| 묶음 | 알림 5건 | 상위 3건 제목 + "외 2건" | 첫 알림의 사운드 1회 |
| 연결 끊김 | 바이낸스 연결 끊김 5분 | 재연결 시도 중 (12회) | warn |
| 절전 복귀 | 감시 중단 구간 있음 | 14:02 \~ 14:47 동안 감시하지 못함 | warn |
| 감시 시작 | blert 감시 시작 | 규칙 6개 · 현물 4 · 선물 2 | 없음 |

숫자는 천 단위 쉼표, 가격은 심볼의 호가 단위 자릿수, 퍼센트는 소수 첫째 자리(펀딩비는 셋째 자리)로 표시한다. 문구는 모두 `src/i18n/ko.json`의 키로 관리한다.

## B8. 설정·데이터 저장

모든 데이터는 사용자 홈 디렉터리 아래 한 폴더에 둔다. 키와 시크릿은 이 폴더에 절대 저장하지 않는다 (B6).

| 데이터 | 파일 | 내용 | 버전 |
| --- | --- | --- | --- |
| 전역 설정 | `config.json` | 사운드 on/off, 언어, 실행 모드, 고지 동의 여부 | v0.1 |
| 알림 규칙 | `rules.json` | B4의 `Rule` 목록 | v0.1 |
| 알림 상태 | `state.json` | B4의 `RuleState` 목록 | v0.1 |
| 설치된 프리셋 | `config.json` 안 | 프리셋 슬러그와 버전 | v0.1 |
| 로그 | `logs/` | 실행 기록 (키 마스킹) | v0.1 |
| 데몬 PID | `blert.pid` | 실행 중인 데몬 프로세스 번호 | v0.4 |
| API 키 | OS 키체인 | 키·시크릿 (파일에 저장 금지) | v0.2 |

### 저장 규칙

| 항목 | 규칙 |
| --- | --- |
| 폴더 | macOS·Linux `~/.config/blert/`, Windows `%APPDATA%\blert\` |
| 형식 | JSON (D-15), 모든 파일 최상단에 `schemaVersion` 필드 |
| 마이그레이션 | `schemaVersion`이 낮으면 시작 시 자동 변환하고 원본을 `.bak`으로 보관 |
| 쓰기 방식 | 임시 파일에 쓴 뒤 교체(원자적 쓰기) + 파일 잠금으로 CLI와 데몬 동시 쓰기 방지 |
| 로그 보관 | 7일 또는 10MB 중 먼저 도달하는 기준으로 오래된 것부터 삭제 |
| 규칙과 상태 분리 | 사용자가 `rules.json`을 백업·공유해도 발동 이력은 섞이지 않음 |

## B9. 실행 모드

세 모드는 같은 감시 코어를 공유하고, 감시 코어를 띄우는 방식만 다르다. 그래야 v0.4·v0.5에서 코어를 다시 짜지 않는다.

| 모드 | 명령 | 버전 | 요구사항 | 동작 |
| --- | --- | --- | --- | --- |
| 포그라운드 | `run` | v0.1 | FR-RUN-01 | 현재 터미널에서 감시 코어 실행, console 어댑터 켜짐 |
| 백그라운드 데몬 | `start` / `stop` / `status` / `logs` | v0.4 | FR-RUN-03 | 분리된 프로세스로 실행, PID 파일로 중복 실행 방지 |
| OS 서비스 | `service install` / `uninstall` | v0.5 | FR-RUN-04 | macOS launchd → Windows 작업 스케줄러 → Linux systemd 순 |

### 절전 복귀 감지 (모든 모드 공통, v0.1)

15초마다 시계를 확인해 직전 확인보다 60초 이상 흘렀으면 절전 복귀로 판단한다. 이때 모든 연결을 재연결하고, 감시가 멈췄던 시작·종료 시각을 warn 알림으로 보낸다 (FR-RUN-02, NFR-REL-02).

### 시작과 종료

1. 시작: 설정 로드 → 스키마 확인·마이그레이션 → (키가 있으면) 권한 검사 → 스트림 연결 → 감시 시작 알림.
2. 종료(Ctrl+C, `stop`, 종료 신호): 새 이벤트 수신 중단 → 상태 저장 → 연결 종료 → PID 파일 삭제.
3. 이미 데몬이 실행 중일 때 `run`이나 `start`를 하면 거부하고 `blert status`를 안내한다.

## B10. 오류 처리·로깅

원칙은 하나다. 감시가 멈추거나 알림을 못 보낼 수 있는 상황은 조용히 넘기지 않고 반드시 사용자에게 알린다.

| 오류 분류 | 예시 | 처리 | 종료 코드 |
| --- | --- | --- | --- |
| 사용자 입력 오류 | 잘못된 심볼, 문법 오류 | 원인 + 올바른 예시 + 오타 제안 | 1 |
| 권한 오류 | 거래·출금 권한 켜진 키, HMAC 키 | 실행 거부 + 바이낸스에서 고치는 방법 안내 | 2 |
| 연결 오류 | 네트워크 끊김, 24시간 만료 | 자동 재연결, 5분 초과 시 warn 알림 | 3 (시작 시 연결 불가일 때만) |
| 외부 API 오류 | 레이트 리밋, 점검 | 대기 후 재시도, 반복되면 경고 | — |
| 출력 오류 | 알림 권한 없음, 사운드 재생 실패 | console로 대체 + 1회 경고 | — |
| 내부 오류 | 예상 못한 예외 | 로그 기록 후 감시 코어 재시작, 3회 연속이면 종료 | 9 |

### 메시지와 로그 규칙

- 사용자 메시지는 "무엇이 문제인지 + 어떻게 고치는지 + 예시" 3요소를 갖추고, 모두 i18n 키로 관리한다 (NFR-UX-02, NFR-UX-03).
- 로그 레벨은 error, warn, info, debug 4단계. 기본은 info, `--verbose`로 debug.
- 로그는 한 줄에 한 이벤트, 시각·레벨·모듈·메시지 순서. 키 형태 문자열은 기록 전에 마스킹한다.

# Part C. 구현 지침

## C. Claude Code 구현 지침

Claude Code는 이 절을 작업 규칙으로 따른다. `CLAUDE.md`에 그대로 옮겨도 된다.

### 작업 규칙

1. 지시받은 버전의 요구사항만 구현한다. 다음 버전 기능을 미리 만들지 않는다.
2. A6 범위 밖 항목은 구현하지도, 제안하지도 않는다.
3. 문서에 없는 결정이 필요하면 임의로 정하지 말고 질문으로 남긴다.
4. 설계와 다르게 구현해야 할 이유가 생기면 먼저 알리고 승인을 받는다.
5. 키·시크릿을 코드, 로그, 테스트 데이터, 커밋에 절대 넣지 않는다.
6. 새 의존성을 추가할 때는 이유를 적고 승인을 받는다.
7. 바이낸스 API 명칭은 구현 시점의 공식 문서로 확인한다.
